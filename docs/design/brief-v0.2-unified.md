# v0.2 設計ブリーフ：計画（WBS）と課題（Issue）を 1 枚の HTML・1 つの JSON に統合する

計画（WBS）と課題（Issue）を1枚の HTML・1つの JSON に統合すると決めた v0.2 の設計ブリーフ（一次記録）。

> 移植元 single-file-issue（非公開リポ） から。v2.0.0 の統合に至る**設計の履歴**として本家に置く（本文は当時の記録のまま。`issue.json` ／ `issue_viewer.html` は現在の `wbs.json` ／ `wbs_viewer.html`）。

> 作成：2026-09-07（PM＝Claude Fable 5.1・作者との壁打ちで確定）。実装ワーカーへの指示書であり、設計判断の一次記録。
> v0.1 の判断は [`brief-v0.1.md`](brief-v0.1.md)。本書はその上に「統合」を載せる。

## 0. 何を作るか（1行）

**WBS Viewer に「計画｜課題」の切替を足し、課題の描画器を同じ HTML に同居させる。データは `projects[]` の中に `tasks`（計画）と `issues`（課題）を並べた 1 つの JSON。つながりは課題側のリンク台帳だけに書き、ビューアが逆引きして両方向へ 1 クリックで飛ぶ。**

## 1. なぜ統合するか（価値の整理・2026-09-07 裁定）

| 誰に | 何が効くか |
|---|---|
| 人 | 計画と課題を 1 か所で読める。行き来が 1 クリック（別タブもファイル選択も無い）。報告（★更新・期限超過）が同じ画面で出る |
| AI | 1 ファイルで突き合わせと参照の検査ができる。「遅れているタスクに紐づく未決の課題を挙げて」が 1 文で済む |

検討して不採用：**A. JSON だけ 1 つ**（ビューア 2 枚のまま＝別の紙芝居を開くたびにファイル選択が要り、手数が減らない）／**C. issue ビューアが wbs.json も読んで吹き出しで見せる**（片方向・読むだけ。統合すれば不要）。
制約の根拠：ローカル直開き（file://）ではページが勝手にファイルを読めず、別タブへ飛ばす手段も無い。切替を同じページ内で行うしかない。

## 2. データ（JSON・v0.2）

### 2.1 形

```json
{
  "name": "自分の課題管理表",
  "holidays": [ "2026-09-21" ],
  "star": { "from": "2026-09-01", "to": "2026-09-07" },
  "projects": [
    {
      "name": "販売管理システム移行",
      "milestones": [ { "date": "2026-10-20", "label": "本番切替", "color": "#cc79a7" } ],
      "tasks":  [ { "id": "2", "name": "変換ツール", "children": [ { "id": "2.3", "name": "文字コード変換", "qty": 1, "hours": 16, "assignee": "ぴぐお", "plan": { "start": "2026-09-14", "end": "2026-09-18" }, "actual": { "start": null, "end": null }, "note": "" } ] } ],
      "issues": [
        { "id": 3, "title": "文字コード変換の仕様が開発部から未回答", "priority": "high", "opened": "2026-09-05", "due": "2026-10-10",
          "ifIgnored": "…", "ifDone": "", "closeWhen": "…",
          "decisions": [ { "q": "対応方針", "since": "2026-09-05", "decided": "2026-09-05", "a": "…" },
                          { "q": "外字をどう扱うか", "since": "2026-09-07", "decided": null, "a": "" } ],
          "pending": { "kind": "waiting", "since": "2026-09-06", "who": "開発部", "until": "2026-09-12", "what": "変換仕様の回答" },
          "closed": null,
          "links": [ { "wbs": "2.3" }, { "issue": 1 }, { "project": "勤怠システム更改", "issue": 2 }, { "title": "仕様書", "url": "https://example.com/spec" } ],
          "actions": [ { "date": "2026-09-05", "text": "開発部へ質問票を送付", "assignee": "ぴぐお", "done": true } ],
          "note": "" }
      ]
    }
  ]
}
```

### 2.2 決めごと

- **案件 ＝ `projects[]` の 1 要素**。計画（`tasks`）と課題（`issues`）は同じ案件の中に並ぶ。**「シート」という言葉と `sheets` キーは廃止**（作者裁定 2026-09-07・異論なし）。
- `tasks` だけの案件（計画だけ）、`issues` だけの案件（課題だけ）、両方ある案件、すべて有効。
- `holidays`／`star` はブック共通（トップレベル）。`milestones` は案件ごと（wbs のまま）。
- 課題の `id` は**案件の中で一意の整数・振り直さない**。WBS の `id` は wbs のまま（文字列 `"2.3"`）。
- **`actions[].wbs` は廃止**（作者裁定：WBS の葉 ＝ 課題 1 件、行動は課題の中の手順。行動を WBS に対応づけない）。
- **`links[]`（リンク台帳）**：課題側だけに持つ。要素は次の 4 形のいずれか（鍵の名前で種類を区別し、混ぜて書けない）：
  - `{ "wbs": "2.3" }` … 同じ案件の WBS タスク
  - `{ "issue": 1 }` … 同じ案件の課題
  - `{ "project": "勤怠システム更改", "issue": 2 }`／`{ "project": "…", "wbs": "1.1" }` … 別の案件
  - `{ "title": "仕様書", "url": "https://…" }` … 外部 URL（`title` 必須・`http(s)` のみ）
- 案件名の変更は、別案件からのリンクの書き換えとセット（説明書に明記。不変キーは今は入れない）。

### 2.3 後方互換（読む側の責任）

| 入力 | 扱い |
|---|---|
| wbs の既存ファイル `{ projects: [{ name, milestones, tasks }] }` | そのまま開ける。課題は空。「課題」表示は空表示 |
| wbs の旧形式 `{ project, milestones, tasks }` | wbs の既存の変換をそのまま |

**課題側に後方互換は持たない**（2026-09-09 裁定）。v0.2 が課題側の**最初の公開形**で、リリース前に外部利用者がいないため、
`sheets`／1枚形の `issues`／`actions[].wbs`／課題レベルの `assignee`／`decision`／`decisionLog`／`pending.reason` は
**読み替えず、検査スクリプトがエラーにする**（混在を許すと、どちらが正か分からない表が増える）。

## 3. 画面

### 3.1 階層

```
操作バー：ファイルを開く／更新／編集 ｜ [計画｜課題] ｜ EN
  計画：今の WBS Viewer（プロジェクト・ガント・時間／進捗タブ・フィルタバー）
  課題：今の Issue Viewer（サマリ＋案件のタブ・フィルタバー・6 列）

- **課題側のフィルタバーの軸**＝状態／優先度／担当／**印**。印のピルは **`待ち` `凍結` `未決` `期限超過` `催促` `★ 更新`**（en `Waiting` `Frozen` `Undecided` `Overdue` `Nudge` `★ Updated`）。**「〜のみ」は付けない**（2026-09-09・作者指摘）。ピルの ON/OFF 自体が「その印が付いた課題だけ出す」を表しており、語尾の「のみ」は重複して読みにくいため。wbs 側（計画ビュー）の **`遅延のみ`** は既存のまま変えない。
```

- **「計画｜課題」は 2 択スイッチ**（wbs の「時間／進捗」タブと同じ作法・片方が塗り）。名前が変わる 1 ボタンにはしない（今何を見ているかと押した先を毎回読み解かせない）。
- JSON に `tasks` しか無ければ「計画」だけ、`issues` しか無ければ「課題」だけを出す（スイッチは出さない）。両方あればスイッチを出し、既定は前回の表示（localStorage）。
- 課題表示の案件タブは `projects[]` の名前。サマリ（案件ごとの集計表）は v0.1 のまま。

### 3.2 リンク台帳の見せ方と、行き来

- **課題側**：タイトル列のタイトルの下に 1 行、小さく薄い文字で `WBS 2.3 ・ 課題 #1 ・ 勤怠 #2 ・ 仕様書`。序列は**タイトル ＞ リンク**（濃さと大きさで弱める。枠・札は使わない＝枠はバッジ専用）。たたんだ時も出す。マウスを置くと下線と少し濃い色。
- **計画側**：課題からリンクされている WBS タスクの行に、小さな `課題 #3` の札（複数なら `課題 #3 #7`）。WBS 側のデータには何も書かない（逆引きは描画時に作る）。タスク名のクリックは既存の折りたたみ操作なので、札のクリックで飛ぶ。
- **飛び方**：同じページ内で表示を切り替え → 案件タブを合わせ → 該当行を開き → スクロール → 2 秒ほど強調。URL の末尾に `#wbs=販売管理システム移行/2.3` または `#issue=販売管理システム移行/3` を書き込み、ブラウザの「戻る」で元へ戻れるようにする。URL を貼って渡された相手は、ファイルを開くと同じ行に飛ぶ（未読込なら「○○ を表示するには JSON を開いてください」の案内）。
- リンク先が無い（WBS 2.3 が存在しない等）は**壊れたリンク**として薄い取り消し線＋ツールチップ（クラッシュしない・データは消さない）。

### 3.3 変えないもの

- wbs の計算式・ガント・イナズマ線・保存の聖域・回帰テスト（構造ゴールデン・ピクセル）。統合で wbs の既存の見た目が 1px も動かないことを回帰網で示す。
- issue の導出規則（状態・★更新・期限超過）・6 列・帯・濃淡・備考の吹き出し。
- **詳細の見出し語（2026-09-07 変更）**：`概要` の中は **`支障：`（`ifIgnored`）／`価値：`（`ifDone`）／`完了条件：`／`方針：`／`待ち：`／`凍結：`／`完了：`**、その下に `実績`／`予定` の帯。en は `Harm:`／`Value:`。**JSON の鍵 `ifIgnored`／`ifDone` は不変**。
- **「方針（未決）」の帯（2026-09-09 追加）**：`概要` の下に、`decisions` の `decided: null` の項目を「・」で列挙し、`since` からの経過日数を添える。決まった項目は帯から消え、概要に `方針：a（M/D）` として並ぶ。

## 4. AI が迷わないためのルール（説明書の冒頭に置く）

**WBS と課題の関係（2026-09-07 議論で修正）**：WBS の大半は課題を持たない「ふつうの計画作業」。課題から生まれた対応だけがリンクで結ばれる。

1. **WBS の葉は課題を持たなくてよい**。ふつうの計画作業（設計・実装・テスト）が大半。
2. **課題を組み込む時は、原則 WBS の葉を 1 つ作り、課題からリンクする**（葉の名前は課題のタイトルに寄せる）。予定・実績・工数は葉に、手順は課題の行動（actions）に書く。**行動ごとに葉を作らない。**
3. 葉を複数に分けるのは、予定日や担当が分かれて計画上の区別が要る時だけ（`links` に `{wbs}` を複数並べる）。
4. **WBS に載せない対応もある**：方針だけで閉じるもの（対応しない・発生せず）、計画の見積や進捗に影響しない小さな手。行動だけで完結してよい。
5. 「#3 を組み込んで」と頼まれたら、**既存の葉があればリンク、無ければ課題タイトルで葉を足してリンク**（既定）。
6. 計画の正は WBS。行動の日付は手順のメモ（統合後は課題の画面にリンク先の葉の予定・実績を薄く添える）。

| 迷いどころ | ルール |
|---|---|
| 番号の種類 | WBS は文字列 `"2.3"`（鍵 `wbs`）、課題は整数 `3`（鍵 `issue`）。鍵の名前で区別する |
| 案件をまたぐ参照 | 同じ案件は `{ "issue": 3 }`、別案件は `{ "project": "…", "issue": 3 }` |
| `null` と「無い」 | 同じ意味。AI が書く時は明示的に `null` |
| 順番 | 配列順＝表示順・時系列。末尾に足す。並べ替えない |
| 担当 | 自由文（`ぴぐお/Aさん`）。集計を頼まれたら割り切って文字列一致 |

**検査スクリプト**（依存ゼロの Python・`scripts/check.py`）：番号の重複・日付の形式・enum（`pending.kind`）・`decisions[]` の形・リンク先の存在（WBS／課題／案件名）・待ちの相手抜け／凍結の再開条件抜け・旧キーの残存（**エラー**）を検査。人は定例前に、AI は編集後に走らせる。

**AI チェックの結果を反映（2026-09-07）**：説明書だけを渡した AI（Sonnet）に利用者役の雑な依頼を 12 本出す検証で見つかった穴（番号が複数案件にある時に黙って片方を編集した／済んだ行動の担当まで書き換えた 等）を、**「依頼が曖昧・矛盾する時の作法」**として `CLAUDE.md`／`CLAUDE.en.md` に節を追加した。

## 6. 決めたこと（2026-09-07・作者裁定）

- 統合する（B が一番価値が大きい）。段階は A → A′ → B。
- 課題は案件（project）の中に置く。シートという言葉と `sheets` キーは廃止。
- WBS のタスクに対応する課題があれば、タスク側の札から 1 クリックで飛ぶ。つながりは課題側のリンク台帳だけに書く。
- 課題番号を WBS の番号（1.1.1）に揃えるのは**やらない**（挿入で番号がずれる・WBS に載せない課題が番号を持てない・保守が増える）。番号は案件内の通し番号のまま、WBS 項番はリンクから導いて隣に表示。
- `actions[].wbs` は廃止（WBS の葉＝課題 1 件、行動＝課題の中の手順）。
- 「計画｜課題」は 2 択スイッチ。リンクで飛んだら「戻る」で戻れる（URL 末尾の目印）。
- 統合ビューアは**まずこのリポ（非公開）で作り**、固まってから wbs リポへ移す（案 2・2026-09-07）。製品名は当面「WBS Viewer」のまま「課題」表示を足す。改名は使ってから決める。
- **画面の見出しを `支障：`／`価値：` にする**（2026-09-07・作者裁定・確定）。en は `Harm:`／`Value:`。JSON の鍵 `ifIgnored`／`ifDone` は不変。
  - 候補＝**影響／価値**・**支障／価値**・弊害／価値・未対応の影響／対応の効果・影響／効果・リスク／価値。
  - **「影響」は不採用**：良い影響・悪い影響の**両方に使える中立語**なので、`ifIgnored`（妨げる側）の欄だと**欄の向きが名前から読めない**。`価値：` と並べると「影響＝悪い方」と暗に読ませることになり、初見で伝わらない。
  - **「支障／価値」を採用**：記事の**「妨げる側／加速させる側」の対**にそのまま重なり、片方を読めばもう片方の向きも分かる。
  - 「効果」は**作業した側の言葉**、「価値」は**受け取る側の言葉**。課題表が測るのは受け取る側なので「価値」。
  - 「リスク」は**不採用**。記事の定義では「まだ起きていないこと」＝表の外にあるものなので、`ifIgnored`（すでに起きている事象の支障も書く欄）とぶつかる。
  - **従来の「影響／効果」欄との対応**は、ツールチップ（見出しにマウスを置くと出す）と説明書（`CLAUDE.md`「起票時のチェック」・README）で示す。現場から来た人が読み替えられるようにする。
  - 期限の説明も **「支障や価値が現れる日」** に揃える（記事の「影響が現れる日・価値を受け取りたい日」と同じことを、欄の名前で言い直したもの）。
- **仕上げ第2弾の裁定（2026-09-09・作者裁定）**
  - **支障／価値の問いと例を固定**：支障「**放置すると、いつ・何が起きるか**」（例：10/20 の本番切替で帳票が読めなくなる）／価値「**やると、いつ・何が得られるか**」（例：11月から、毎月の締め作業が半日で終わる）。空欄の欄に何を書けばよいか、例で分かるようにする。
  - **画面のボタン名**：`決定を記録` → **`方針を決める`**、`閉じる` → **`クローズ`**（en `Decide`／`Close`）。記事の4つの動き「載せる・決める・組み込む・閉じる」は**記事の言葉として残し**、説明書に「画面のボタンは『方針を決める』『クローズ』」と対応を書く。
  - ~~**1課題1方針＋履歴 `decisionLog`**~~ → **同日中に撤回**。`decisions[]`（`{ q, since, decided, a }`）へ一本化し、1課題が方針も未決も複数持てる形にした（下の「`decisions[]` に一本化」の項）。
  - **リンクの追加・削除を画面から**（編集モードの `＋リンク` フォームと各リンクの `✕`）。**リンク行は1行1リンク**にし、**備考の印は詳細末尾からタイトル下のリンク行へ移す**（たたんだままでも備考が読める）。
  - **`＋課題` は絞り込みバーの右端**（編集モード中だけ）。**追加後は自動でその行へ移動**する。
  - カレンダーの表示位置の修正は**仕様に影響しない**（実装の直しのみ）。
- **状態と印の整理（2026-09-09・作者裁定）**
  - **状態は3つだけ**：**未着手**（済んだ行動なし）／**対応中**（済んだ行動あり）／**完了**（`closed`）。「どこまで手が動いたか」だけを表す。
  - **未決・待ち・凍結は状態ではなく印**。印は6つ＝**待ち／凍結／未決 N／⚠ 期限超過／⚠ 催促／★ 更新**。**完了行には ★ 以外の印を出さない**（もう追いかけない。★ だけは「今週これを閉じた」が報告の中身なので残す）。
  - 理由＝実際の表は「対応中だが未決が3件」「未着手だが相手待ち」が普通で、1つの状態列に押し込めると**動いているのか止まっているのかが読めなくなる**。
- **`decisions[]` に一本化（2026-09-09・作者裁定）**：`decision`／`decisionLog` を廃止し `{ q, since, decided, a }` の配列に。`decided` が入った項目＝**方針**（概要に `方針：a（M/D）` として複数行）、`decided: null`＝**未決**（帯「**方針（未決）**」に「・」で列挙・`since` からの経過日数つき）。
  - 帯の名前の候補＝**判断／論点／決めること／方針（未決）**。**「論点」は新人に難解**、**「決めること」は冗長**、「判断」は決めた結果と紛れる。**「方針（未決）」を採用**（概要の `方針：` と同じ語で、括弧が「まだ決まっていない」を示す）。
  - **記号「問／決」は作者の判断で撤回**（1文字の記号は覚えないと読めない。語で書く）。
  - 「TODO 型は載せた時点で decision を書く」の規則は**廃止**（未決が無ければそのまま未着手／対応中で読める）。ボタン「方針を決める」も廃止し、帯の各行の `＋方針`／`✕` で編集する。※行頭のボタンは**同日中に `確定` へ変更**（編集行を**1行レイアウト**にし、左から `確定`／決めるべきこと／期限欄〈placeholder `期限 MM-DD`〉／`✕`。`確定` を押すと答えのフォームが開く）。経過日数の表記は **`N日経過（M/D〜）`**（表示・編集とも同じ）。
- **ペンディングを「待ち」「凍結」の2つに（2026-09-09・作者裁定）**：`pending: { kind: "waiting", since, who, until, what }`／`{ kind: "frozen", since, resumeWhen, detail }`。
  - 理由＝**現場のペンディングは「待ち」が最多**で、そこに**相手（`who`）と期限（`until`）**を持たせると **⚠ 催促が導出できる**（人が覚えておく必要がなくなる）。`reason` の3値では、待ちに期限を書く場所が無かった。
  - 記事の3理由との対応＝**決まっていない → `decisions[]` の未決**（ペンディングにしない）／**揃っていない → 待ち**／**止めている → 凍結**。打ち手（決める人に持ち込む・催促する・再開条件を書く）は記事のまま。
  - **状態ではなく印にした**のは上と同じ理由。待ちながら手が動いていることは普通にある。

- **仕上げ第3弾の裁定（2026-09-09・作者裁定）**
