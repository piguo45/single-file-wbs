# ADR-0008: 状態を持たず、事実から導出する

> 移植元 single-file-issue（非公開リポ） の **ADR-0001** を v2.0.0 の統合で本家へ移した（本文は当時の記録のまま）。
> 移植元では課題データを `issue.json`、ビューアを `issue_viewer.html` と呼んでいた。v2.0.0 以降はどちらも **`wbs.json` ／ `wbs_viewer.html`** に統一されている。

`wbs.json` は事実（決めた・止めた・閉じた・行動が済んだ）だけを持ち、状態（未着手／対応中／完了）と印はビューアが導出する。

## ステータス
承認済み（v0.1・基盤決定）

## コンテキスト
課題管理表には必ず「ステータス」列がある。Excel でも `未対応／対応中／保留／完了` を手で選ぶ。
だがこの列は**人が手で書く**ため、実態と食い違う。「方針は決めたのにステータスが未対応のまま」「閉じたのに対応中」は現場で日常的に起きる。
状態をデータに持つか、事実から計算するかの選択。

## 決定
`issue.json` が持つのは次の**事実**だけ：

- `decision`（いつ・どう決めたか）／ `pending`（いつから・なぜ止まっているか）／ `closed`（いつ・どう閉じたか）

状態は `issue_viewer.html` が毎回この3つから導出する（詳細は [`CLAUDE.md`](../../CLAUDE.md) の「導出値」節）：

| 事実 | 導出される状態 |
|---|---|
| `closed` あり | 完了 |
| else 済んだ行動（`done: true`）が1件でもある | 対応中 |
| else | 未着手 |

（v0.1 は `pending`／`decision` も状態に混ぜていたが、**2026-09-09 に状態3つ＋印6つへ整理**した。下の「結果」参照。）

**期限超過**（本日 > `due` かつ未完了）と **★**（報告期間に動いた行）も同じく導出値で、データには書かない。

## 理由
- **ズレが構造的に起きない**：状態列が無いので「閉じたのに対応中」が発生しようがない。
- **AI が書きやすい**：AI は「閉じた事実」だけ書けばよく、状態列との整合を負わない。書き忘れによる片手落ちが減る。
- **なぜ止まっているのかが必ず残る**：「保留」だけの列は理由を持てない。`pending` が「待ち（誰を・何を・いつまで）」か「凍結（再開条件）」かを持つので、止まっている理由が必ず添う。
- 計画側の [ADR-0003（派生値をデータに持たせない）](0003-no-derived-values-in-data.md) と同じ原則（工数・進捗が派生値なのと同じ理由で、状態も派生値にする）。

検討して却下：`status` 列を持ち事実と併記する（二重管理でズレる）／状態を持ち事実を持たない（なぜそうなったかが消える）。

## 結果
- `status`／`state`／`overdue` 等のキーは**書いてはいけない**（受け入れ基準4で検査する）。
- 「実行が終わったら閉じる」型（TODO的な行）は、v0.1 では載せた時点で `decision` を書く運用にした（**2026-09-09 に廃止**。決めることが無ければ未決0件として扱う）。
- 止まっていることは状態ではなく**横断的な事実**になった。方針が決まっていても、物や返事を待って止まれる。
- **状態は3つ、あとは印になった（2026-09-09 追記）**：状態＝**未着手／対応中／完了**（済んだ行動の有無と `closed` だけで決まる）。**未決（`decisions` の `decided: null`）・待ち・凍結・⚠ 期限超過・⚠ 催促・★ 更新は「印」**で、状態と重ねて付く。「対応中だが未決が3件」「未着手だが相手待ち」が普通に起きるので、1つの状態列に押し込めると動いているのか止まっているのかが読めなくなる。印もすべて事実からの導出で、データには書かない。
- **催促は待ちと未決の両方から出る（2026-09-09 追記）**：`⚠ 催促` は「待ちの期限切れ」「未決の期限切れ（`decisions[].until`）」「待っていた課題が完了したのに解除していない」の3つから導出する。**追いかけ忘れを人の記憶に頼らない**ための印で、これも事実からの導出（データには書かない）。
- **★の期間だけは設定として持つ（2026-09-07 追記）**：★を「報告期間に動いたもの」（期間内に済んだ行動／決めた・止めた・閉じた）に変えたのに伴い、トップレベルに `star: { from, to }` を置いた。★が**どの行に付くか**は従来どおり導出値だが、**期間は導出できない**（報告する人が決めるもの）。報告する人・読む人・AI が同じ★を見るために JSON に持つ＝`_progress` と同じ「ある時点の人の判断＝事実」の扱いで、「派生値を持たせない」方針と矛盾しない。不正な `star` は無視して既定の直近7日に落とす。
- **担当も導出値になった（2026-09-06 追記）**：課題レベルの `assignee` を廃止し、担当は `actions[].assignee` だけに持つ。**独立した担当列は置かず**、担当は行動行に `担当：ぴぐお` の形で出す。**たたむと詳細列が次の一手（`done:false` の最初の1件）1行だけ**になり、そこにも同じ形で担当が出る（未の行動が無ければ空欄・完了の課題は常に空欄／2026-09-07 追記）。「課題の担当」と「次に動く人」が食い違う余地を構造から消した。旧データの `issue.assignee` は読まない（保存では消さない）。
